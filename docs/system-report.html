Chapter 3 · System Analysis

3.1 System Analysis

The system is a browser-based examination platform with three actors — the teacher (examiner), the student (candidate), and the system itself (automated proctoring, grading and background workers). A teacher uploads course material as a PDF, from which the system generates multiple-choice and short-answer questions using a large language model. Students join an exam with a short PIN, take it under continuous in-browser proctoring, and receive AI-assisted grades that a teacher can review. The analysis below fixes the requirements the software must satisfy and establishes that building it is feasible.

3.1.1 Requirement Analysis

i. Functional Requirements

Functional requirements state what the system does. They are grouped by module and each is independently verifiable.

IDRequirementDescription
FR-1Account & session managementRegister and authenticate teachers and students; issue short-lived access tokens with rotating, revocable refresh tokens; log out (server-side revocation); change password with current-password re-authentication; enforce role-based access to teacher-only endpoints.
FR-2Exam authoringA teacher creates an exam, uploads a source PDF (≤ 10 MB), and the system generates MCQ and short-answer questions with Bloom-level tags via an LLM. The teacher sets duration, an optional recurring availability window, subject/group linkage, and a "require Safe Exam Browser" flag.
FR-3Roster & access controlRestrict joining by opt-in email roster or by group membership; auto-provision guest student accounts on first join; access an attempt via its capability identifier.
FR-4Exam takingJoin by 6-character PIN, resume an in-progress attempt, autosave answers (debounced), flag questions, and submit. Enforce the availability window and SEB requirement at join.
FR-5Identity verificationEnrol a student's face once from five guided poses (1024-d embeddings, no raw image stored); capture one embedding during the exam for advisory match against enrolment.
FR-6Proctoring & lockdownDetect and log: face absence, multiple faces, gaze direction, voice / multiple speakers, mobile phones and books (object detection), virtual machines, multiple monitors, Safe Exam Browser, and in-page screen capture. Enforce fullscreen, block tab-switching, copy/cut/paste, DevTools/print shortcuts, back-navigation, and right-click; terminate on a three-strike rule.
FR-7Evidence captureCapture a single webcam snapshot only at flagged moments (extra/absent/returned face, phone, book, termination), throttled and quota-bounded; never continuous recording.
FR-8Live invigilationStream proctoring events and attempt-lifecycle changes to the teacher in real time over an authenticated WebSocket, powering a live roster dashboard.
FR-9GradingGrade MCQs deterministically and short answers semantically with an LLM (score, correctness, feedback); allow a teacher to override any mark (human-in-the-loop).
FR-10ReportingPresent per-attempt answers, a proctoring-event timeline, a gaze scatter plot, an evidence gallery, ML review records, and an aggregated academic performance report.

ii. Non-Functional Requirements

Non-functional requirements constrain how well the system performs its functions — the quality attributes an examiner cares about.

IDAttributeRequirement
NFR-1SecurityBackend tokens never exposed to page JavaScript (held in an encrypted, httpOnly cookie and injected by a server-side proxy); JWT rotation with reuse detection and a Redis revocation list; per-IP rate limiting on login, registration, refresh and exam-join; strict Content-Security-Policy and framing / MIME / referrer headers; upload validation by magic bytes and size; single-use WebSocket auth tickets.
NFR-2PerformanceUI interactions respond within ~100 ms; proctoring telemetry is throttled per event type and batched (one request per 5 s); answers autosave on a 600 ms debounce; webcam runs at 320×240 and object detection at a sparse 2.5 s interval to bound CPU/GPU cost.
NFR-3ScalabilityStateless JWT API scales horizontally; heavy work (question generation, grading, ML review) is offloaded to Celery workers; Redis backs rate limiting, tickets and revocation. (The in-process WebSocket manager is single-worker; multi-worker fan-out via Redis pub/sub is a documented upgrade.)
NFR-4ReliabilityRate limiter and token store fail open on a Redis outage so a cache failure never locks out authentication; grading tasks retry with exponential backoff; the live WebSocket reconnects with backoff and a heartbeat.
NFR-5UsabilityGuided enrolment, clear violation warnings before termination, one-click PIN sharing, and non-blocking error toasts; the exam surface is distraction-free.
NFR-6PrivacyNo continuous screen or video recording; only 1024-d face embeddings leave the browser, never raw frames; evidence is limited to flagged-moment snapshots governed by an allowlist and per-attempt quotas.
NFR-7MaintainabilityModular routers/services/hooks, fully typed (TypeScript + Pydantic), 54 automated unit tests, structured JSON logging with request IDs, and global exception handlers.
NFR-8PortabilityContainerised (Docker Compose); S3-compatible object storage (MinIO locally, AWS S3 in production unchanged); runs on any modern Chromium/Firefox browser with a webcam.

3.1.2 Feasibility Analysis

i. Technical Feasibility

The project stands on mature, well-supported technologies: Next.js 16 / React 19 on the client, FastAPI with SQLAlchemy on the server, PostgreSQL, Redis and MinIO for data, and Celery for background work. All proctoring inference (face landmarks, gaze, object detection) runs in the browser via MediaPipe Tasks Vision (WebAssembly + WebGL) and @vladmandic/human, so no server-side GPU is required — a decisive simplification. The browser APIs relied upon — getUserMedia, WebGL, WebAssembly, WebSocket, the Fullscreen and Clipboard APIs — are supported by all current target browsers. The remaining technical risks are known and bounded: tuning the Content-Security-Policy for the WASM pipelines, the camera-permission requirement, and the single-worker WebSocket limitation (with a clear Redis-pub/sub upgrade path). The project is therefore technically feasible.

ii. Operational Feasibility

The workflow maps directly onto how examinations already run: a teacher prepares an exam and shares a PIN; students join and sit it; results and an invigilation record follow. Learning curve is minimal — teachers manage exams from a dashboard, students need only a PIN and a webcam. The privacy-first design (snapshots at flagged moments rather than full-screen recording) materially improves candidate acceptance and eases institutional data-protection sign-off. For high-stakes papers the teacher can require Safe Exam Browser. The main operational dependency is a candidate device with a working webcam and modern browser; where hardware is weak the system degrades gracefully (telemetry is throttled, detection sparse). The system is operationally feasible for a single-institution deployment.

iii. Economic Feasibility

Development cost is principally student time. The runtime stack is almost entirely free and open-source and self-hosted, so there is no per-candidate proctoring licence — commercial live-proctoring services typically charge on the order of US$8–15 per candidate per exam. The only metered dependency is the LLM API (Google Gemini) used for question generation and short-answer grading, whose cost is a few US cents per exam and is incurred only at authoring and grading time, not during invigilation. Indicative running costs are below.

iv. Schedule Feasibility

The work decomposes into sequential-but-overlapping phases that fit a single academic project timeline. Each phase produced a demonstrable increment, de-risking the schedule.

Algorithm Details

The system's distinctive behaviour lives in a handful of algorithms spanning client-side vision, telemetry control, and server-side security. The most significant are given below in pseudocode.

Algorithm 1 — Gaze estimation from iris landmarks

INPUT : 478 face landmarks L from MediaPipe FaceLandmarker
OUTPUT: gaze direction, away flag, yaw, pitch

for each eye e in {right, left}:
    width_e  = |L[inner_e].x - L[outer_e].x|
    if width_e < epsilon: return CENTER          # eye too small / bad frame
    hRatio_e = (L[iris_e].x - L[outer_e].x) / (L[inner_e].x - L[outer_e].x)
hRatio = mean(hRatio_right, hRatio_left)          # 0 = temple, 1 = nose
vRatio = (L[iris_R].y - L[top_R].y) / |L[bottom_R].y - L[top_R].y|

direction = CENTER
if   hRatio < 0.28: direction = RIGHT
elif hRatio > 0.72: direction = LEFT
elif vRatio < 0.25: direction = UP
elif vRatio > 0.80: direction = DOWN
away = (direction != CENTER)
# "gaze_away" fires only if away persists > 4 s (see Algorithm 2)

Algorithm 2 — Per-type throttling and batched delivery

STATE: lastFired[type] = 0 ;  buffer = [] ;  flush every 5 s

function canFire(type, minGapMs):        # dampens high-frequency signals
    now = currentTimeMillis()
    if now - lastFired[type] < minGapMs: return false
    lastFired[type] = now ;  return true

function onEvent(ev):                     # from every monitor
    buffer.push(ev)                        # coalesced into one request
    if ev.type in EVIDENCE_WORTHY and now - lastCapture >= 8000:
        captureWebcamFrame() -> upload    # flagged-moment snapshot only

every 5 s: if buffer not empty: POST buffer ; buffer = []
on pagehide: navigator.sendBeacon(buffer) # never lose the tail

Algorithm 3 — Fixed-window rate limiting (Redis, fail-open)

INPUT : bucket name b, client IP, limit N, window W seconds
key = "ratelimit:" + b + ":" + clientIP
try:
    count = REDIS.INCR(key)
    if count == 1: REDIS.EXPIRE(key, W)
    if count > N:
        ttl = REDIS.TTL(key)
        raise HTTP 429 with Retry-After = ttl
except RedisError:
    log() ; ALLOW request      # availability > strict limiting

Algorithm 4 — Refresh-token rotation with reuse detection

INPUT : presented refresh token T (claims: sub, jti, exp, type=refresh)
verify signature and type ; else 401
if REDIS.exists("revoked_jti:"+T.jti): 401           # already revoked
status = markRefreshUsed(T.jti, T.exp):
    if SETNX("refresh_used:"+T.jti): return "ok"      # first use
    else: return (now - usedAt <= 30 s) ? "ok" : "reused"
if status == "reused": 401 "reuse detected"           # stolen-token replay
issue new access + new refresh (fresh jti)             # rotation

Algorithm 5 — Advisory face verification

INPUT : session embedding s (1024-d), enrolment set E for the student
best = min over e in E of  euclidean(s, e)             # L2 distance
review = { kind: "face", distance: best, flag: "needs_review" }
persist(review)          # advisory only — never blocks or auto-fails
# no raw frame is transmitted; only the numeric embedding leaves the browser

Algorithm 6 — Single-use WebSocket ticket handshake

MINT (authenticated REST, teacher):
    verify teacher owns the attempt/exam channel
    ticket = randomUrlsafe(32)
    REDIS.SET("ws_ticket:"+ticket, {channel, userId}, EX=60)   # 60 s TTL
    return ticket

CONNECT (WebSocket, ?ticket=...):
    data = REDIS.GETDEL("ws_ticket:"+ticket)     # atomic: single use
    if data == null or data.channel != requestedChannel:
        accept then close(4401)                  # unauthorised
    else: subscribe(channel) ; answer "ping" with "pong"

5.1.2 Implementation Details of Modules

Authentication module. Credentials are verified by FastAPI against bcrypt hashes; the server issues an access token (60 min, carrying a jti) and a rotating refresh token (30 days). NextAuth v5 holds both inside an encrypted, httpOnly session cookie. A Next.js catch-all proxy route (/api/backend/[...path]) decrypts the cookie server-side, injects the Authorization header, and refreshes expired tokens transparently, so no backend token is ever readable by page JavaScript. Refresh tokens are single-use with a 30-second grace window; replay outside it is treated as theft and rejected, and logout revokes both tokens via a Redis jti denylist.

Exam authoring module. A teacher uploads a PDF straight to MinIO via a size-capped presigned POST; the backend parses it (pymupdf) and a Celery task calls Gemini to generate MCQ and short-answer questions with Bloom tags. Exams carry a unique 6-character PIN, an optional recurring availability window (institution timezone), subject/group linkage, and the require_seb flag.

Proctoring module. React hooks drive the monitors on the exam page. useProctoringMonitor runs MediaPipe FaceLandmarker each animation frame for face-count, absence and gaze; useObjectDetection runs EfficientDet-Lite0 sparsely (2.5 s) for phones and books; useAudioMonitor analyses the microphone for voice and multiple speakers; useEnvironmentCheck flags VMs, extra monitors, screen capture and SEB; and useExamSecurity enforces fullscreen, blocks copy/paste, DevTools shortcuts, back-navigation and right-click, and applies the three-strike termination. All signals are throttled per type and batched every five seconds, with a sendBeacon flush on page-hide.

Evidence module. When an event on the evidence allowlist fires, one webcam frame is drawn to a canvas, encoded as JPEG and posted to a capability-based endpoint that validates it by magic bytes and size and enforces per-attempt quotas before storing it in MinIO. Teachers view snapshots through short-lived presigned URLs in an evidence gallery.

Live invigilation module. A teacher's browser mints a single-use WebSocket ticket over the authenticated proxy, then connects to an exam-level channel. The backend broadcasts every proctoring event and attempt-status change to that channel; the roster updates live (event counts, risk indicator, new joiners, submissions) with heartbeat and backoff reconnection.

Grading module. On submission, a Celery task grades MCQs by exact option match and short answers via a structured Gemini prompt returning score, correctness and feedback. A teacher can override any mark; overrides are recorded (graded_by = TEACHER) and the total recomputed. Advisory face, anomaly and fairness workers attach ML-review records without gating the result.

5.3 Result Analysis

All 54 unit tests (43 backend + 11 frontend) pass, and the frontend additionally passes strict type-checking (tsc), linting (ESLint) and a production build (next build). The thirteen system scenarios behave as specified. The test suite deliberately concentrates on the security-critical and correctness-critical logic — token rotation and revocation, rate limiting, WebSocket ticketing, upload validation, the evidence privacy gate, SEB detection and the VM/throttle heuristics — because these are the parts whose silent failure would most undermine examination integrity.

Functionally, the system meets every requirement in §3.1.1: exams are authored with AI assistance, candidates are proctored across nine independent signal families, invigilators watch in real time, and responses are graded with a human-in-the-loop. Against the non-functional targets, the throttling-and-batching design keeps network traffic low (one telemetry request per five seconds regardless of signal volume) and the debounced autosave prevents request floods; the fail-open security primitives preserve availability during a cache outage; and the privacy posture holds — only embeddings and flagged-moment snapshots ever leave the browser.

Two limitations are recorded honestly. First, computer-vision inference runs on the browser's main thread, so very low-end hardware can experience UI jank — moving inference to a Web Worker is the remedy. Second, the WebSocket manager is single-worker; horizontal scaling of live invigilation requires the documented Redis pub/sub upgrade. Neither affects correctness at single-instance scale, and both have clear, low-risk resolutions.

Chapter 6 · Conclusion and Future Work

6.1 Conclusion

This project set out to build a fast, secure and well-featured computer-based assessment platform, and delivered one that is credible on all three counts. Examinations are authored with AI assistance from ordinary course PDFs, candidates are proctored entirely in the browser across face, gaze, audio, object, environment and behavioural signals, invigilators observe in real time, and answers are graded semantically with a teacher able to review every mark. Crucially, the platform reaches this capability without the two costs that define commercial proctoring: it needs no per-candidate licence and no full-screen surveillance. Inference runs on the candidate's own device, only numeric embeddings and flagged-moment snapshots are transmitted, and the security architecture keeps authentication tokens out of reach of page scripts while rate-limiting and revoking them server-side. The result is a system whose integrity guarantees are proportionate and defensible rather than merely maximal — the correct trade-off for an institutional deployment.

6.2 Future Recommendations

  • Cryptographic SEB enforcement. Upgrade the current presence check to full Browser-Exam-Key / Config-Key hash validation, distributing exams with a matching .seb configuration so SEB cannot be spoofed by user-agent alone.
  • Off-main-thread inference. Move the MediaPipe and Human pipelines into a Web Worker (OffscreenCanvas) to eliminate UI jank on low-end devices.
  • Continuous identity verification. Re-verify the candidate's face periodically rather than once, and enable liveness/anti-spoof detection to defeat photo attacks.
  • Horizontally scalable invigilation. Replace the in-process WebSocket manager with Redis pub/sub so live monitoring survives multiple API workers.
  • Trained anomaly & fairness models. Replace the placeholder z-score anomaly worker with the intended sequence model once enough graded attempts exist, and add a protected-attribute field to enable genuine subgroup fairness auditing.
  • Composite risk scoring. Fuse the per-type violation counts into a single, explainable per-attempt trust score to help teachers triage review.
  • Load & soak testing. Add end-to-end and load tests (Playwright + a WebSocket load harness) to complement the current unit suite before large-cohort use.
  • Accessibility & mobile. Broaden support for assistive technology and evaluate a constrained mobile-tablet exam mode.
